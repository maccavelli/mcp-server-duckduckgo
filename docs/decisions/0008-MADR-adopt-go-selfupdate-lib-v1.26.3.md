# Adopt go-selfupdate-lib v1.26.3 for the update command and the release workflow

## Context and Problem Statement

`mcp-server-duckduckgo update` still constructs its updater from `github.com/maccavelli/mcplib/selfupdate`. The release job still calls mcplib's reusable publish workflow at a pin commented as mcplib v1.4.1, and it still passes `bridge-release: false`. The build job still compiles with `make build-all`, writes `SHA256SUMS` by hand, and checks one linux binary's `--version` string. The maintained library, the maintained build workflow, and the maintained publish workflow are `github.com/maccavelli/go-selfupdate-lib` at tag `v1.26.3`. [0003-MADR-update-dependency-pins.md](0003-MADR-update-dependency-pins.md) left that replacement as a separate decision. This record is that decision. It covers the command and the release workflow together, because the install scripts the owner asked for are produced only by the library build workflow.

The command has to keep working as a Cobra subcommand of an MCP server. `update` must skip configuration, write no JSON-RPC on the protocol stdout, return errors to `main` so the in-process tests survive, and install a standalone binary for the three platforms this repository already publishes. The owner asked for install scripts. The library generates `install.sh` and `install.ps1` only when the release spec sets `installer` and CI calls `build-selfupdate-release.yml`. Windows on ARM was considered as a fourth platform and is not part of this decision (E18).

The owner also asked to scope in the disclosure check and the verify check, taken from another repository and housed in `go-shared`. The disclosure scan is one script. `verify` is this repository's Makefile target, and it calls that script. Both are part of this decision (E19). `go-shared` `docs/decisions/0003-MADR-house-disclosure-check.md` is the decision that adds the script.

## Considered Options

* **A. Library surface inside the existing Cobra command, with the library build workflow and generated installers.** `cli.Flags.Bind`, `Flags.Request`, `cli.Run`, `buildinfo` stamps, `DefaultHTTPClient`, `UserAgent`, `DiscardReporter` and `NonInteractiveConfirmer` as the updater's placeholders, `NewStandaloneInstaller`, the three platforms, an `identity` command, `selfupdate-release.json` with an `installer` object, and both peeled `v1.26.3` workflows. The `validate` job keeps its pins and its golangci-lint install, and runs `make verify`. `make disclosure-check` calls the `go-shared` script with `--repo`. `main` keeps `selfupdate.ExitCode` and one stderr print.
* **B. Import-path swap only.** Point the current constructors at `go-selfupdate-lib`, and keep the hand-rolled flags, the 15-minute `http.Client` timeout, the hand-rolled context timeout, `NewTextReporter`, `NewTerminalConfirmer`, `RawVersion` / `RawBuildKind`, the Makefile release build, and the mcplib workflow pin.
* **C. Replace the command with `cli.Command`.** The guide's primary sample: one call parses flags, runs the update, prints the failure line, and returns the exit code.
* **D. Stay on `mcplib/selfupdate`.** Leave `update.go`, `version.go`, the Makefile stamps, the hand-rolled build job, and the mcplib workflow pin as they are.
* **E. Copy the `prepare-commit-msg` workflow.** Take its path filters, concurrency, Node 24 setting, native test matrix, six-platform spec, coverage target, `scripts/verify-scripts.sh`, its `tools` bootstrap, and both release workflows.
* **F. Add windows/arm64 to option A.** Ship a fourth platform so `install.ps1` succeeds on a machine whose registry architecture is `ARM64`.

## Decision Outcome

Chosen option: "A. Library surface inside the existing Cobra command, with the library build workflow and generated installers.", because that option uses the library for the flags, the contradiction checks, the run, the stamps, the HTTP client, the release build, the install scripts, and the publisher, and it leaves the Cobra command, the skip-config annotation, the stdout trap, the in-process tests, the validate job's pins, and the mcplib server harness in place. The disclosure script comes from `go-shared`. `make verify` is the quality target the validate job runs. Options E and F add a native matrix, path filters, and a platform this decision does not need (E17, E18, E19).

The concrete shape:

1. Require `github.com/maccavelli/go-selfupdate-lib v1.26.3`. `go 1.26.11`, `toolchain go1.27.4`, `mcplib v1.6.0`, `x/sys v0.50.0`, `x/mod v0.43.0`, and `x/term v0.48.0` stay (E1, E12). `fetchup` stays `v0.3.0`. Playwright stays on `github.com/mxschmitt/playwright-go`.

3. The updater constructor takes no writer. The update request uses `Identity().Current()` with the `v` kept, because that is what `Flags.Request` puts in `CurrentVersion` (E10). Local `make` still passes `VERSION` and `BUILD_KIND`. CI does not call those recipes.

It carries `selfupdate.skip-config=true`, `cobra.NoArgs`, `SilenceUsage: true`, and `SilenceErrors: true`. `RunE` writes `buildinfo.Identity().String()` and a newline to `OriginalStdout`. `Execute` has saved that file before it points `os.Stdout` at `os.Stderr` (E3). A nil `OriginalStdout` returns an error and does not construct a line. Success returns nil. The build workflow and both installers run this command and read the first process-stdout line (E16). `RootCmd.Version` stays the trimmed display string in item 7. `Identity().String()` is the identity line, including the parenthesized kind. The tag job's linux `--version` awk check compares a different string and leaves with the hand-rolled build job (E5, E7, E16).

One product, name `mcp-server-duckduckgo`, package `./cmd/mcp-server-duckduckgo`, `identity_args` of `identity`. Platforms linux/amd64, darwin/arm64, and windows/amd64, in that order. Packaging `binary`. `installer.name` is `mcp-server-duckduckgo`, which derives the environment prefix `MCP_SERVER_DUCKDUCKGO` (E16). No hooks, no extras, no `tags`, and no prerelease channels.

* Good, because `DefaultHTTPClient` has no `Client.Timeout`, so the run context is the bound on a download. The current constructor sets a 15-minute client timeout and a 15-minute context together (E4, E10).
* Good, because `mcplib v1.6.0` stays for the harness, and the floor and toolchain stay on the 0007 pair (E1, E2, E12).
* Good, because `--json` can write to the stdout `Execute` saved, while every other update byte stays on the command error stream (E3, E13).
* Good, because `--help` still prints when `SilenceUsage` and `SilenceErrors` are set (E10).
* Good, because `install.sh` and `install.ps1` are generated from the library templates, and the identity job runs the staged binary on `ubuntu-24.04`, `macos-15`, and `windows-2025` (E16).
* Good, because `extra-assets-json` is a build output, so the publish workflow receives the scripts the same run generated.
* Good, because one `make verify` runs the test, vet, and golangci-lint `v2.15.0` checks the validate job used to list separately, and it adds the format check, the module check, the record gates, and the disclosure scan (E7, E19).
* Good, because the home-path rules live in one `go-shared` script. A fix there is the fix every consumer runs (E19).
* Neutral, because a failure line from `main` is the error text. `cli.Exit` would prefix `update failed:`, and calling it from `RunE` as well as `main` would print twice. `SilenceErrors` is what keeps Cobra from adding a third copy.
* Neutral, because a local-build `--check` returns `ErrUpdateAvailable` and the library's selected event mentions `--force` (E14). Exit code 10 still means an actionable check. Applying that local build still takes `--force`.
* Neutral, because `v9.9.9-rc.1` with kind `release` is `KindRelease` (E11). This workflow passes `prerelease-channels-json` through from the build output. With no channels in the spec, that output is the workflow default `[]`, so stable tags are what publish (E9, E16). Publishing a prerelease tag is a later decision.
* Neutral, because an unstamped `go install` can report the module version through `Current()`, while an unstamped `go build` in this module reports `dev` (E11). The trimmed display string follows `Current()`.
* Neutral, because a ref that is not a tag rehearses the build, including the three identity runners. Publish runs when `rehearsal` is `false` (E16).
* Neutral, because SHA256SUMS does not list extra assets, and the generated scripts are extra assets (E16). Each script checks the program asset against SHA256SUMS.
* Bad, because a binary stamped `BUILD_KIND=release` whose `VERSION` is not a release tag is a local build (E11). Today's `buildKind` treats any exact `release` stamp as `ReleaseBuild`, including a dirty `git describe`. CI tag builds pass the tag name, so a published tag binary still qualifies. A local `make build BUILD_KIND=release` on a dirty describe does not.
* Bad, because a published binary follows the library recipe: `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=true`, and no `-tags netgo` or `-extldflags '-static'` (E16). Local `make build` and `make linux` keep those two flags. The spec lists no `tags`, so the stage check expects an empty tag set.
* Bad, because `identity` has to write the saved stdout. After `Execute`, `fmt.Println` writes the aliased stderr, and the identity job then rejects the empty stdout line (E3, E16).
* Bad, because `install.ps1` on a Windows machine whose registry architecture is `ARM64` exits when the release has no windows/arm64 asset (E18). That machine can still run the windows/amd64 binary under emulation if the file is copied into place. This decision accepts that installer gap because the published shipment share is small and this server has no install count (E18).

* Bad, because the guide's own closing check still names `v1.26.2`, and section 5 still shows that release's workflow SHA (E13). Following those lines would pin the previous release. The pin in this decision is the peeled `v1.26.3` commit.
* Bad, because `make verify` fails until the sibling checkout contains `scripts/check_disclosure.py`, and the validate job fails until the public `go-shared` commit that added that file can be fetched into `runner.temp` (E19, E21).
* Neutral, because the second tree is a tokenless git fetch. The checkout action pin stays on this repository's own checkout (E21).
* Good, because `govulncheck` `v1.10.0` already reports no reachable vulnerability in this module, and `make verify` will fail when a later database does (E20).

## Pros and Cons of the Options

### A. Library surface inside the existing Cobra command, with the library build workflow and generated installers

* Good, because the scratch module already built `Flags.Bind`, `Flags.Request`, `cli.Run`, `DefaultHTTPClient`, `UserAgent`, `NewStandaloneInstaller`, and the stamp rule against `v1.26.3` (E10, E11).
* Good, because the same peel generates `install.sh` and `install.ps1` from `installer`, and the scratch parse of this spec returned both names and the prefix `MCP_SERVER_DUCKDUCKGO` (E16).
* Good, because the build workflow's outputs are the publish workflow's inputs, so the hand-rolled artifact name, platform JSON, and empty extra-asset list leave together (E7, E9, E16).
* Good, because the skip-config annotation, the saved stdout, and `main`'s exit mapping stay, which is what the current tests and the MCP pipe require (E3, E6).
* Good, because the three platforms already have identity runners: `ubuntu-24.04`, `macos-15`, and `windows-2025` (E16).
* Good, because `make verify` calls one `go-shared` disclosure script with `--repo`, and the validate job fetches that repository outside this tree (E19, E21).
* Neutral, because the failure line stays `main`'s print of the error text, and the library's `update failed:` prefix stays unused.
* Bad, because the release rule is stricter than the string compare in `buildKind` (E5, E11).
* Bad, because `install.ps1` will not install onto Windows on ARM (E18).

### B. Import-path swap only

* Good, because `NewGitHubSource`, `NewExactAssetSelector`, `NewStandaloneInstaller`, `NewStrictVersionPolicy`, `ExitCode`, and `ErrUpdateAvailable` keep their names, so the current `update.go` compiles after the import edit.
* Neutral, because `go.sum` still changes, and the tests still move to the new module path.
* Bad, because the 15-minute `Client.Timeout`, the hand-rolled flags, and the `main.RawVersion` stamps remain, which is the surface `buildinfo` and `cli` exist to replace (E4, E10).
* Bad, because the Makefile release job would remain, so the library would not generate `install.sh` or `install.ps1` (E7, E16).
* Bad, because the publish job would keep the mcplib workflow pin and `bridge-release`, while the workflow at `v1.26.3` has no such input (E7, E9).

### C. Replace the command with `cli.Command`

* Good, because one library call then owns flag parsing, help text, the `update failed:` line, signals, and the timeout (E13).
* Neutral, because the guide demonstrates that call on `prepare-commit-msg`, whose `main` is not this Cobra tree.
* Bad, because `cli.Command` has no way to carry `selfupdate.skip-config`, so configuration would load on `update` unless a Cobra wrapper remained, at which point the wrapper is option A.
* Bad, because the guide's Cobra sample calls `os.Exit` inside `RunE`. The tests in E6 run the command in-process. An `os.Exit` there ends the test process.
* Bad, because `cli.StdioOptions().Stdout` after `Execute` is the aliased stderr, so `--json` would miss the saved protocol stdout (E3, E13).

### D. Stay on `mcplib/selfupdate`

* Good, because the current tests already pass on `main` and no publish pin moves.
* Neutral, because `mcplib v1.6.0` remains a dependency under every option, for the harness (E2).
* Bad, because the updater, the stamps, the build job, and the publisher stay on the older surface, including a workflow input the maintained workflow does not declare (E4, E7, E9).
* Bad, because 0003 already recorded this replacement as a separate decision, and the library tag now matches the floor and toolchain this module declares (E1, E8).
* Bad, because the owner asked for install scripts, and this option does not generate them (E16).

### E. Copy the `prepare-commit-msg` workflow

* Good, because that workflow already calls both library workflows and passes the rehearsal flag into the publish condition (E17).
* Neutral, because path filters, a docs workflow, and a Node 24 setting are documentation and action-runtime choices. They do not generate a release asset.
* Neutral, because option A adds `make disclosure-check` and `make verify` through `go-shared`. Copying the whole workflow is no longer what brings those two targets in (E19).
* Bad, because the copied `verify` also runs coverage, workflow-lint, tools-test, and build-all, and `verify-scripts.sh` requires `tools/` plus `check_ci_filters.py`, which this repository does not have (E19). Its govulncheck pin is `v1.8.0`, installed by the `tools` bootstrap. Item 12 runs `v1.10.0` with `go run` (E20).
* Bad, because the six-platform spec includes `darwin/amd64`, which the library's identity map does not run, and includes `linux/arm64` and `windows/arm64`, which this decision does not ship (E16, E17, E18).
* Bad, because a native `go test ./...` matrix would run this server's Playwright tests on macOS and Windows. That is a separate quality decision, and this record does not measure it.

### F. Add windows/arm64 to option A

* Good, because `install.ps1` would then find a windows/arm64 asset on a machine whose registry architecture is `ARM64`, and `windows-11-arm` is a standard hosted runner the library already maps (E16, E18).
* Neutral, because the Go server is a small process. An amd64 binary of it can run under emulation when someone copies the file into place. The installer is the piece that refuses (E18).
* Bad, because the published estimates put Windows on ARM at about 3.2% of laptop shipments in 2026, and this repository has no install count against which to weigh a fourth identity job (E15, E18).
* Bad, because the frozen platform list in `update.go` and the release spec would both have to grow, and every later tag would publish an asset for that share (E4, E18).
